**Multiple Vault Support — Design Record**
Decisions and discussion from a Grill with Docs session, 2026-09-07

Produced by walking the design tree question-by-question against the E2O API
contract and the existing plugin code. Terminology lives in `/CONTEXT.md`; the
two decisions that warranted it are written up as ADRs in `/docs/adr/`. This
file is the narrative record: what was asked, what was rejected, and why.

---

## 0) Starting premise, corrected

The session opened on "I have recently introduced the option to support
multiple vaults." That was true of the **service**, not this plugin.

`grep -rniE "vaults|multiVault|vaultId|vaultName" src/` returned two hits, both
an incidental comment about "large vaults". Specifically: `EmailSummary`
(`src/api.ts:8`) and `EmailDetail` (`:36`) carry no `vault` field,
`EmailListRequest` (`:15`) has no `vault` param, `EmailListResponse` (`:22`)
has `tags?` but no `vaults?`, and `Plan/1. API end points.md` still documents
the pre-vault response shape.

So there was no plugin-side implementation to review. The session designed one.

## 1) Server contract this design assumes

From the service-side documentation supplied during the session:

- `vault` is a plain nullable string on the email object — no object, no array,
  no `@@` prefix, no quotes. Present on both `GET /api/emails/:id` and each row
  of `GET /api/emails`.
- `GET /api/emails` also returns a top-level `vaults: string[]` facet — all
  distinct non-null vaults for the user, sorted, cached ~5 minutes. It is a
  facet over the whole table, not just the current page.
- `?vault=<name>` filters the list. Raw name, not the `@@` token.
- Senders write either `@@Work` (bare, ends at first whitespace) or
  `@@"Second Brain"` (quoted, the only way to get spaces). Both normalise to a
  bare name before storage; the plugin never sees quotes or the marker syntax.
- At most one vault per email. First valid token wins; later ones are stripped
  and ignored.
- Names may contain spaces (quoted form only), are otherwise
  `[A-Za-z0-9_-]`, trimmed at the edges, max 64 chars.
- `hashtags` may be `null`, not `[]` — it is a nullable JSON column.
- Routing is plan-gated (`canUseVaults`). Starter is excluded, and on those
  accounts the `@@` token is left in the subject text unparsed. A subject can
  therefore literally contain `@@Work` while `vault` is null.

## 2) Terminology

Two collisions were found and resolved. Both are recorded in `/CONTEXT.md`
under Flagged ambiguities.

**"vault" meant two things.** `Vault` is an Obsidian API class, already bound
as `vault` throughout `runSync` (`src/pipeline.ts:2`, `:30`, `:45`). The new
server concept is a routing name on an email. Resolved: the local directory
tree is an **Obsidian Vault**; the routing name is a **Vault Marker**; the bare
identifier `vault` stays reserved for Obsidian's handle in plugin code.

**"tag" meant three things** — Obsidian's own `#tag`, the `hashtags` field
(`src/api.ts:12`, written to frontmatter at `src/helpers.ts:154`), and the
`?tag=` filter (`src/api.ts:19`). Note that `?tag=` and `?vault=` are sibling
params on the same endpoint filtering different things, so conflating them in
prose would produce wrong code. Resolved: the email-side concept is a
**Hashtag**, and a Vault Marker is never called a tag. An earlier proposal of
"Vault Tag" was withdrawn for this reason.

An email with no marker is an **Unmarked Email**.

## 3) What a Vault Marker selects

**Question:** when an email carries `"vault": "Second Brain"`, does that name a
folder inside one Obsidian Vault, or does it name a whole Obsidian Vault?

**Decision: it names a whole Obsidian Vault.**

A user has several vaults on their machine — work, personal, art — and marks
each email for one of them. Every install sees the same full stream and imports
only its own slice. The Work install declines the art email; the Art install
takes it.

Consequence: markers never become folder paths, so the sanitisation question
that the 64-char / space-permitting name format would otherwise raise does not
arise. Notes continue to land in `notesFolder` exactly as today.

## 4) Unmarked emails — the receive policy

**Question:** an install claims a marker. What does it do with email that has
none? Per the contract this is the *common* case.

Three facts forced the answer:

1. Starter accounts can never produce a marker at all.
2. Every existing install today is unmarked-only. If claiming a marker meant
   taking only that marker, every current user's sync would go empty on
   upgrade.
3. Installs cannot coordinate. Settings and the fetch log both go through
   `plugin.saveData` (`src/fetch-log-store.ts:62`), scoped to one Obsidian
   Vault. The Work install has no channel to the Art install, so "exactly one
   vault catches the unmarked ones" can only ever be a setting.

**Rejected — every install takes unmarked email:** a three-vault user gets
three copies of every unmarked email, and unmarked is the common case.

**Rejected — no install takes unmarked email:** silently drops mail, and
Starter users would sync nothing at all.

**Decision: a three-way per-install setting, defaulting to everything.**

```
This vault receives:
  (•) All emails                                      ← default
  ( ) Only emails marked for [__________] vault
  ( ) Emails marked for [__________] vault, and unmarked emails
```

The default is byte-for-byte the pre-feature behaviour, so upgrading an
existing install changes nothing and no one's sync silently empties. Routing is
opt-in. The catch-all is an explicit choice visible in one vault's settings
rather than an invariant spread across three machines.

Written up as `docs/adr/0001-per-install-receive-policy.md`.

**Constraint on the implementation:** when `vault` is null, the plugin must not
fall back to parsing `@@` out of the subject. That is the obvious-looking fix
for Starter users and it would hand out the entitlement the server deliberately
withheld. Unmarked means `vault === null`, full stop.

**Accepted limitation:** a user who sets up two of their three vaults and
wonders why the third receives nothing is making a user error, and the plugin
does not try to prevent it.

## 5) Where filtering happens

**Question:** filter server-side via `?vault=`, or locally in the plugin?

**Decision: locally. `?vault=` is deliberately not used.**

Filtering is inherently per-install — the same email is a decline in Work and
an accept in Art — so no server-side filter is right for more than one of a
user's vaults at a time. The third receive policy can't be expressed as one
`?vault=` request anyway, since the filter excludes nulls and there is no
`?vault=none`.

Cost is small and bounded: summaries carry no body and no attachments, and the
expensive `getEmail` call happens per selected email
(`src/pipeline.ts:99`), so declining before that line skips the body and every
attachment download.

Written up as `docs/adr/0002-filter-locally-not-on-the-wire.md`.

**Paired decision — declined ids go in the fetch log, marked as declined.**
`paginateEmails` stops at the first already-logged id
(`src/pipeline.ts:252`) on the assumption that the log is a contiguous run of
the newest emails. Filtering locally would make the log sparse and break that
assumption. Logging declines keeps it true.

When a user changes their receive policy, drop the declined entries; the next
ordinary `fetch-new` then reconsiders that mail. This is deliberately *not*
solved by telling users to run "Fetch all notes" — see defect 5 below.

## 6) Supplying the marker, and matching it

**Question:** how does a user enter the marker, and how is it compared?

**Can a plugin enumerate the machine's Obsidian vaults? No.** The string
`vaults` appears nowhere in obsidian 1.1.1's typings. The three `getName()`
declarations (`obsidian.d.ts:706`, `:1253`, `:3689`, on `DataAdapter`,
`FileSystemAdapter` and `Vault`) all return the *current* vault's name. A
plugin is scoped to the vault it runs in.

That turns out not to matter, because each install already knows the one name
that counts — its own.

**Decision: a dropdown, populated from the `vaults` facet plus the current
Obsidian Vault's name, with free text still permitted.** Free text has to stay,
because the facet is ~5-minute cached and a marker used for the very first time
won't appear in it yet. The facet arrives on the list response and the settings
tab already calls `listEmails` in `testConnection` (`src/main.ts:375`), so
populating it is close to free.

**Decision: prefill with `this.app.vault.getName()` when it appears in the
facet.** A user whose vaults are already named Art, Work and Personal gets
three correctly-configured installs with no typing.

**Decision: matching is case-insensitive** (after trimming). `Work` and `work`
name the same Obsidian Vault. Recorded in `/CONTEXT.md` under Relationships.
If the marker namespace turns out to be case-sensitive server-side, two
casings will appear as separate facet entries and the plugin will merge them.
Investigated and deliberately dropped: merging is the behaviour a user would
expect, so the server's answer doesn't change the plugin.

**Decision: report declines in the sync notice** — `12 added, 3 skipped, 5 not
for this vault`. One counter, and it turns a silent drop into something a user
can see. The notice is built at `src/pipeline.ts:207`.

## 7) One marker per install, or several?

**Decision: one.** A user whose vault should receive two markers consolidates
them into one name. Rejected a multi-select to keep setup simple; it stays
cheap to add later, since `normalizeSettings` already rewrites every stored
field on load.

## 8) Existing notes

**Question:** an install switches from "All emails" to "marked for Art". Its
vault already holds months of work and personal notes. What happens to them?

**Decision: nothing, ever.** The plugin never moves or deletes a note in
response to a policy change. Those files are the user's by then — edited,
linked, embedded — and the risk is not worth a tidiness win. Notes written
before this feature also carry no marker, so identifying them would cost a
`getEmail` round-trip per note.

**Decision: stamp new notes with the marker** — `email2obsidianVault: Art` in
frontmatter, alongside the existing `email2obsidianID` (`src/helpers.ts:154`),
key omitted for unmarked email. One line in `renderEmailMarkdown`, and it makes
a note self-describing about why it landed where it did, so a future cleanup or
re-route feature can work locally for everything except the pre-existing tail.

## Implementation surface

- `src/api.ts` — add `vault: string | null` to `EmailSummary`/`EmailDetail`,
  `vaults?: string[]` to `EmailListResponse`. Do **not** add a `vault` param to
  `EmailListRequest`.
- `src/main.ts` — receive-policy setting (three-way + marker dropdown),
  prefill from `vault.getName()`, facet fetch, sentence-case copy.
- `src/pipeline.ts` — filter `selected` before the `getEmail` loop; declined
  counter into the notice; declined ids into the log; drop declined entries on
  policy change.
- `src/fetch-log-store.ts` — represent declined entries.
- `src/helpers.ts` — `email2obsidianVault` frontmatter key.

## Defects found along the way

These pre-date the feature and were surfaced while reading the code.

1. **Null hashtags fail the whole email.** `isEmailDetailResponse` requires
   `Array.isArray(obj.hashtags)` (`src/api.ts:236`) and the field is typed
   `string[]` (`:12`), but the contract says it may be null. Such an email
   throws `ApiError('bad-response')` and never syncs. Live today, independent
   of markers. Note `renderEmailMarkdown` already handles null correctly
   (`src/helpers.ts:153`), so the guard is stricter than its consumer, and
   `isEmailListResponse` doesn't check hashtags at all — an email can list fine
   and then fail on detail.
2. **`vault` absent from every type** — blocks implementation, see above.
3. **Pagination can loop forever.** In `paginateEmails` (`src/pipeline.ts:242`
   onward), if the server returns `hasMore: true` with `nextCursor: null`,
   `cursor` becomes `undefined` and page one is refetched indefinitely.
   `fetch-new` is accidentally shielded by the early-stop; `fetch-all` is not.
4. **`stoppedEarly` is computed and never used** beyond a debug log
   (`src/pipeline.ts:70`, `:80`).
5. **`fetch-all` duplicates rather than reconciles.** `safeFilename`
   (`src/helpers.ts:27`) suffixes against the folder scan from
   `src/pipeline.ts:62`, so re-fetching an email whose note exists writes
   `Meeting notes-1.md` beside `Meeting notes.md` — for every note in the
   vault. Untested: `tests/pipeline.test.ts` has one test and it is
   `fetch-new`. This is why section 5 recovers from policy changes via the
   fetch log rather than a re-fetch.
6. **Lint is red — 17 errors**, 5 of them `obsidianmd/ui/sentence-case` on
   existing settings copy (`src/main.ts:220`, `:232`, `:260`, `:288`, `:376`).
   New settings copy must be sentence case or it adds to the count.
