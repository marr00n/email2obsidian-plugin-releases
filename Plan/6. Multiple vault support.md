**Multiple Vault Support — Design Record**

Two Grill sessions: 2026-09-07 on mechanism, 2026-09-09 on user experience.
This file is the consolidated narrative record — what was asked, what was
rejected, and why. The decisions that warranted it are written up tersely as
ADRs in `/docs/adr/`; terminology lives in `/CONTEXT.md`. The ADRs are
self-contained, so this document is background rather than required reading.

## 0) Starting premise, corrected

The first session opened on "I have recently introduced the option to support
multiple vaults." That was true of the **service**, not this plugin.

`grep -rniE "vaults|multiVault|vaultId|vaultName" src/` returned two hits, both
an incidental comment about "large vaults". There was no plugin-side
implementation to review. The session designed one.

Since then the Service Client rebuild (commit `6ff99e8`) has landed the wire
half: `EmailSummary` and `EmailDetail` now carry `vaultMarker: string | null`,
normalised from the server's `vault` field (`src/api.ts:47`, `:369`, `:391`).
Nothing consumes it yet.

## 1) Server contract this design assumes

Full detail in `docs/server-api-contract.md`. The load-bearing facts:

- `vault` is a plain nullable string on the email object — no object, no array,
  no `@@` prefix, no quotes. Present on both `GET /api/emails/:id` and each row
  of `GET /api/emails`.
- `GET /api/emails` also returns a top-level `vaults: string[]` facet — all
  distinct non-null vaults for the user, sorted, cached ~5 minutes. It is a
  facet over the whole table, not just the current page.
- `?vault=<name>` filters the list. Raw name, not the `@@` token.
- Senders write either `@@Work` (bare, ends at first whitespace) or
  `@@"Second Brain"` (quoted, the only way to get spaces). Both normalise to a
  bare name before storage; the plugin never sees quotes or the marker syntax.
- At most one vault per email. First valid token wins; later ones are stripped
  and ignored.
- Names may contain spaces (quoted form only), are otherwise
  `[A-Za-z0-9_-]`, trimmed at the edges, max 64 chars.
- `hashtags` may be `null`, not `[]` — it is a nullable JSON column.
- Routing is plan-gated (`canUseVaults`). Starter is excluded, and on those
  accounts the `@@` token is left in the subject text unparsed. A subject can
  therefore literally contain `@@Work` while `vault` is null.
- **The service deletes an email after 72 hours.** It is a short-lived queue,
  not a store; the plugin holds the durable copy. This single fact drives the
  answer to three separate design questions below.

## 2) Terminology

Two collisions were found and resolved. Both are recorded in `/CONTEXT.md`
under Flagged ambiguities.

**"vault" meant two things.** `Vault` is an Obsidian API class, already bound
as `vault` throughout `runSync` (`src/pipeline.ts:2`, `:30`, `:45`). The new
server concept is a routing name on an email. Resolved: the local directory
tree is an **Obsidian Vault**; the routing name is a **Vault Marker**; the bare
identifier `vault` stays reserved for Obsidian's handle in plugin code.

**"tag" meant three things** — Obsidian's own `#tag`, the `hashtags` field, and
the `?tag=` filter on `GET /api/emails`. Note that `?tag=` and `?vault=` are
sibling params on the same endpoint filtering different things, so conflating
them in prose would produce wrong code. Resolved: the email-side concept is a
**Hashtag**, and a Vault Marker is never called a tag. An earlier proposal of
"Vault Tag" was withdrawn for this reason.

An email with no marker is an **Unmarked Email**.

## 3) What a Vault Marker selects

**Question:** when an email carries `"vault": "Second Brain"`, does that name a
folder inside one Obsidian Vault, or does it name a whole Obsidian Vault?

**Decision: it names a whole Obsidian Vault.**

A user has several vaults on their machine — work, personal, art — and marks
each email for one of them. Every install sees the same full stream and imports
only its own slice. The Work install declines the art email; the Art install
takes it.

Consequence: markers never become folder paths, so the sanitisation question
that the 64-char, space-permitting name format would otherwise raise does not
arise. Notes continue to land in `notesFolder` exactly as today.

## 4) The receive policy, and the control that expresses it

**Question:** an install claims a marker. What does it do with email that has
none? Per the contract this is the *common* case.

Three facts forced the shape of the answer:

1. Starter accounts can never produce a marker at all.
2. Every existing install today is unmarked-only. If claiming a marker meant
   taking only that marker, every current user's sync would go empty on
   upgrade.
3. Installs cannot coordinate. Settings and the fetch log both go through
   `plugin.saveData` (`src/fetch-log-store.ts:62`), scoped to one Obsidian
   Vault. The Work install has no channel to the Art install, so "exactly one
   vault catches the unmarked ones" can only ever be a per-install setting.

**Rejected — every install takes unmarked email:** a three-vault user gets
three copies of every unmarked email, and unmarked is the common case.

**Rejected — no install takes unmarked email:** silently drops mail, and
Starter users would sync nothing at all.

**Decision: two settings, defaulting to everything.**

```
Vault markers                                          [Pro]

Markers          [ Work; Second Brain                       ]
                 Semicolon-separated. Leave blank to receive every marker.
                 Each vault is set up separately. A vault left blank
                 receives everything — including mail marked for your
                 other vaults.
                 Last fetch declined: Art (4), Wrok (1)

Unmarked emails                                          [ON]
                 Emails sent without a marker.
```

All copy is placeholder — see Not yet decided.

**Blank means every marker.** It is the absence of a filter, not an empty allow
list. That is what makes the release safe: the default state is blank markers
plus unmarked on, which is byte-for-byte the pre-feature behaviour. Existing
installs upgrade silently, no migration runs, and no first-run prompt
interrupts the majority of users who have one vault and no interest in this
feature.

Which markers a vault takes and whether it takes unmarked email are orthogonal
questions, so they are two controls rather than options within one.

Written up as `docs/adr/0001-per-install-receive-policy.md`.

### Controls considered and rejected

**A three-way radio group with a single marker** (all emails / only emails
marked for X / X plus unmarked). This was the 2026-09-07 decision, and it is
what the first version of ADR 0001 recorded. It forced a user whose vault
should receive two markers to consolidate them into one name server-side —
changing their sending habits to suit the plugin's UI — and it bundled the two
orthogonal questions into one control.

**A checkbox list seeded from the `vaults` facet.** Rejected on the 72-hour
retention window. The facet only ever shows markers used in the last three
days, so a user with three vaults who has emailed only one of them this week
sees one row. The other two vaults exist; the server cannot know it. A control
whose contents silently omit most of the answer is worse than a plain text
field, because it looks authoritative. Facet-driven autocomplete was rejected
for the same reason in softer form.

**An "any other marker" wildcard toggle beside the list.** Rejected because it
has to default to on for upgrade safety, and while it is on the markers field
does nothing — a new user's first action would produce no observable change.
Folding "everything" into the blank state removes the toggle and the dead state
with it.

### Constraint on the implementation

When `vault` is null, the plugin must not fall back to parsing `@@` out of the
subject. That is the obvious-looking fix for Starter users and it would hand
out the entitlement the server deliberately withheld. Unmarked means
`vault === null`, full stop. The one exception is section 7.

### Accepted limitations

There is an allow list but no deny list — a vault cannot say "everything except
Art".

**A typo is silent.** `@@Wrok` routes nowhere, raises no error, and the email is
deleted after 72 hours. Section 6 is the mitigation.

A user who sets up two of their three vaults leaves the third taking every
email, including mail marked for the other two. Only settings copy can steer
this, so the markers field says so directly.

## 5) Where filtering happens, and what a policy change releases

**Question:** filter server-side via `?vault=`, or locally in the plugin?

**Decision: locally. `?vault=` is deliberately not used.**

Filtering is inherently per-install — the same email is a decline in Work and
an accept in Art — so no server-side filter is right for more than one of a
user's vaults at a time. A vault taking both its listed markers and unmarked
email can't be expressed as one `?vault=` request anyway, since the filter
excludes nulls and there is no `?vault=none`. Neither can a vault listing
several markers.

Cost is small and bounded: summaries carry no body and no attachments, and the
expensive `getEmail` call happens per selected email (`src/pipeline.ts:98`), so
declining before that line skips the body and every attachment download.

Written up as `docs/adr/0002-filter-locally-not-on-the-wire.md`.

**Paired decision — declined ids go in the fetch log, marked as declined.**
`paginateEmails` stops at the first already-logged id (`src/pipeline.ts:254`)
on the assumption that the log is a contiguous run of the newest emails.
Filtering locally would make the log sparse and break that assumption. Logging
declines keeps it true.

**Changing the markers is retroactive, and announced before it happens.**
Widening the list releases mail that was previously declined — up to 72 hours
of it may still be on the server. The settings tab states what will arrive at
the moment of the edit — `Art: 7 emails from the last 3 days will arrive on the
next fetch` — with a Fetch now button, then drops the matching declined
entries so the next ordinary `fetch-new` picks them up.

The count is a local lookup against the fetch log, not a server request: a
declined entry stores its marker and timestamp, so the number is free, instant
and available offline.

**Rejected — forward-only:** a user who mistypes a marker at setup and corrects
it ten minutes later would lose that mail permanently, and "Fetch all notes" is
not a safe recovery route while it duplicates rather than reconciles (defect 5
below).

**Rejected — a silent backfill:** same behaviour without the announcement. A
burst of notes appears at a moment the user didn't choose, possibly hours
later, mid-writing session.

## 6) Entering markers, matching them, and seeing what was declined

**Can a plugin enumerate the machine's Obsidian vaults? No.** The string
`vaults` appears nowhere in obsidian 1.1.1's typings. The three `getName()`
declarations (`obsidian.d.ts:706`, `:1253`, `:3689`, on `DataAdapter`,
`FileSystemAdapter` and `Vault`) all return the *current* vault's name. A
plugin is scoped to the vault it runs in.

**Decision: free text, semicolon-separated.** Whitespace cannot be the
separator because markers may legally contain spaces (`Second Brain`), and a
semicolon is not legal inside a marker, so it parses unambiguously. Entries are
trimmed and duplicates collapsed.

**Rejected — prefill from `app.vault.getName()`.** The 2026-09-07 session
proposed it as zero-typing setup. A vault's name and its marker are often
different strings — a user may have named the vault "Second Brain" and be
sending `@@sb` — and a wrongly pre-filled marker routes mail silently.

**Decision: matching is case-insensitive** (after trimming). `Work` and `work`
name the same Obsidian Vault. Recorded in `/CONTEXT.md` under Relationships.
If the marker namespace turns out to be case-sensitive server-side, two casings
will appear as separate facet entries and the plugin will merge them.
Investigated and deliberately dropped: merging is the behaviour a user would
expect, so the server's answer doesn't change the plugin.

**Decision: name declines, don't only count them.** This is the mitigation for
the silent typo accepted in section 4, and it is diagnostic rather than
suggestive — it reports what was turned away and never proposes a marker.

- The sync notice gains one counter: `12 added, 3 skipped, 5 not for this
  vault`. The notice is built at `src/pipeline.ts:219`.
- The settings tab carries a passive read-only line beneath the markers field:
  `Last fetch declined: Art (4), Wrok (1)`.

A typo appears there by name the first time mail carrying it is turned away. So
does an unconfigured sibling vault: seeing `declined: Personal (12)` is how a
user learns that Personal exists in their stream and is presumably still taking
everything.

## 7) The Starter-plan trap

Vault routing is gated at ingest, not at read. On Starter without a grant,
`vault` is always null **and** the `@@Work` token is left in the subject. That
user sees notes titled `@@Work Weekly review`, a markers field that receives
nothing however they fill it in, and — if they ever switch unmarked off — a
vault that receives nothing at all. The reasonable conclusion is that the
plugin is broken.

**Decision: warn in settings; leave the note title alone.**

The signature is cheap to detect and cannot occur on an entitled account:
`vault` null on a summary whose subject begins with `@@`. Once seen, the
markers section shows an informational notice pointing at the user's plan. It
never blocks anything.

**Rejected — also stripping the `@@` token from the note title.** It crosses
the line drawn in section 4 (the plugin would be parsing a marker the server
deliberately withheld) and it deletes the visible evidence that makes the
warning credible.

**The plugin cannot know the user's plan and must not try.** The service
branches no route on plan, and the gate is ingest-only, so a downgraded account
still returns non-null `vault` values on older rows. The markers section is
*labelled* Pro but always remains editable — never disabled, never hidden —
because a lapsed pro user with months of marked mail still needs the control
that filters it.

## 8) Notes: what gets stamped, and what gets left alone

**Question:** an install narrows its markers. Its vault already holds months of
work and personal notes. What happens to them?

**Decision: nothing, ever.** The plugin never moves, deletes or re-stamps a
note in response to a change of markers. Those files are the user's by then —
edited, linked, embedded — and the risk is not worth a tidiness win. Notes
written before this feature also carry no marker, so identifying them would
cost a `getEmail` round-trip per note, and past 72 hours it cannot be done at
all.

**Decision: stamp new notes uniformly.** `email2obsidianVault` goes into
frontmatter alongside the existing `email2obsidianID` (`src/helpers.ts:159`),
written on every note and left as an empty string for an Unmarked Email rather
than omitted.

```yaml
---
email2obsidianID: 42
email2obsidianVault: Art
---
```

**Rejected — omitting the key when unmarked** (the 2026-09-07 decision).
Unmarked is the common case, so most notes would lack the property and every
Bases or Dataview query over it would need a null branch. The cost of the
alternative is one empty property in the properties panel.

**Rejected — not stamping at all.** With a 72-hour retention window, a note
older than three days cannot be re-interrogated to find out which marker
brought it in. Anything not stamped at write time is unrecoverable, and any
future cleanup or re-route feature would have nothing local to work from.

Written up as `docs/adr/0003-notes-record-their-vault-marker.md`.

## Implementation surface

- `src/api.ts` — **done** in commit `6ff99e8`: `vaultMarker: string | null` on
  `EmailSummary` and `EmailDetail`, normalised from the server's `vault`
  field. Do **not** add a `vault` param to `EmailListRequest`. The `vaults`
  facet on the list response is not needed by settings; add it only if
  something else wants it.
- `src/main.ts` — `markers: string[]` and `receiveUnmarked: boolean` on
  `Email2ObsidianSettings`, defaulting to `[]` and `true`. Semicolon parsing,
  trimming and case-insensitive dedupe in `normalizeSettings`. The two
  controls, the decline readout, the pending-backfill line with its Fetch now
  button, the overlap warning, the Pro label, the plan warning.
- `src/pipeline.ts` — decide each summary before the `getEmail` call
  (`src/pipeline.ts:98`), so a decline skips the body and every attachment
  download. Declined counter into the notice (`src/pipeline.ts:219`). Declined
  ids into the log. Drop the matching declined entries when markers change.
- `src/fetch-log-store.ts` — a declined entry needs its marker and timestamp,
  so the backfill count can be computed locally and bounded to the 72-hour
  window.
- `src/helpers.ts` — `email2obsidianVault` in `renderEmailMarkdown`
  (`src/helpers.ts:159`).

New settings copy must be sentence case, or it adds to the `sentence-case` lint
count in defect 6.

## Defects found along the way

These pre-date the feature and were surfaced while reading the code. Status
checked 2026-09-10.

1. ~~**Null hashtags fail the whole email.**~~ **Fixed** in commit `6ff99e8`.
   `isEmailDetailResponse` required `Array.isArray(obj.hashtags)` while the
   contract says the field may be null, so such an email threw
   `ApiError('bad-response')` and never synced. The rebuilt Service Client
   coerces rather than rejects (`src/api.ts:368`, `:390`).
2. ~~**`vault` absent from every type.**~~ **Fixed** in commit `6ff99e8` —
   `vaultMarker` now carried through both shapes.
3. **Pagination can loop forever.** Still live. In `paginateEmails`
   (`src/pipeline.ts:244` onward), if the server returns `hasMore: true` with
   `nextCursor: null`, `cursor` becomes `undefined` and page one is refetched
   indefinitely. `fetch-new` is accidentally shielded by the early-stop;
   `fetch-all` is not.
4. **`stoppedEarly` is computed and never used** beyond a debug log. Still live
   (`src/pipeline.ts:81`, `:242`).
5. **`fetch-all` duplicates rather than reconciles.** Still live. `safeFilename`
   (`src/helpers.ts:27`) suffixes against the folder scan from
   `src/pipeline.ts:63`, so re-fetching an email whose note exists writes
   `Meeting notes-1.md` beside `Meeting notes.md` — for every note in the
   vault. **This is load-bearing for section 5**: it is why a policy change
   recovers via the fetch log rather than by telling users to re-fetch.
   Note that per `CLAUDE.md` the `-1` behaviour is accepted for ordinary
   `fetch-all` use, because nothing older than 72 hours is still on the server;
   the problem is only that it cannot serve as a reconciliation path.
6. **Lint copy count.** Reported as 17 errors at the 2026-09-07 session, 5 of
   them `obsidianmd/ui/sentence-case` on existing settings copy
   (`src/main.ts:220`, `:232`, `:260`, `:288`, `:376`). Not re-verified —
   dependencies are not installed in the review environment.
