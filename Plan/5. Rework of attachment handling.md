**Draft Future Attachment Flow**
Step-by-step plan for base64-driven inline attachments

Goal: Inline images are decoded from Markdown data URIs into the same attachment folder used for non-inline attachments (honoring user settings), `contentDisposition === 'inline'` API attachments are ignored, collisions dedupe across both sources via shared `uniqueFilename` handling, non-base64 URIs are rejected and logged, and all failures surface as `AttachmentSaveError`—with as much shared code as possible between inline and non-inline flows.

1) Shared folder + binary save pipeline (`src/attachments.ts`)
   - Create `resolveAttachmentTarget({ noteFolder, attachmentFolder })`:
     - Normalize inputs, decide target (attachment folder or note folder), and ensure the target exists (single place that calls `ensureFolder`).
     - Return `{ noteFolderPath, attachmentTargetPath }` to pass downstream.
   - Add `saveBinaryData({ data, suggestedName, targetFolder, mimeType? })`:
     - Sanitize `suggestedName` (reuse/extend current sanitizeAttachmentName).
     - Derive extension from MIME via `getExtensionForMime` (fallback `.bin`).
     - Call `uniqueFilename` to dedupe within `targetFolder`.
     - Write with `writeBinaryFile`; on failure throw so caller wraps with `toAttachmentSaveError`.
   - Add `getExtensionForMime(mime: string): string` with a small map; default to `.bin`.

2) Common naming + error helpers (`src/attachments.ts` or shared util)
   - Add `buildAttachmentBase({ source: 'inline' | 'api', emailId, index, suggestedName?, mimeType? })`:
     - For API: prefer sanitized `suggestedName` (original filename) else `attachment-${emailId}-${index}` plus MIME-derived extension.
     - For inline: prefer sanitized alt text if present, else `inline-${emailId}-${index}` plus MIME-derived extension.
   - Broaden `AttachmentSaveError` to accept either an `AttachmentMeta` or an `InlineAttachmentContext`:
     - `InlineAttachmentContext` includes `emailId`, `placeholderIndex`, `mimeType?`, `dataUriSnippet?`.
   - Add `toAttachmentSaveError(context, err)`:
     - Accepts either meta or inline context plus the thrown error/issue string.
     - Normalizes to `{ context, message }` for both API and inline callers.

3) Adjust API attachment saving (`src/attachments.ts:42-181`)
   - Input: `{ vault, apiKey, attachments, noteFolder, attachmentFolder, logger?, downloader? }`.
   - Resolve folders once via `resolveAttachmentTarget` and reuse the returned paths.
   - Filter: skip any `AttachmentMeta` with `contentDisposition === 'inline'`.
   - For each remaining attachment:
     - Build base name with `buildAttachmentBase({ source: 'api', emailId: att.id, index, suggestedName: att.fileName, mimeType: att.mimeType })`.
     - Download via `downloader(att.id, apiKey, baseName)`; on failure push `toAttachmentSaveError(att, err)` and continue.
     - Call `saveBinaryData({ data: downloaded.data, suggestedName: baseName, targetFolder, mimeType: downloaded.mimeType })`; on failure push `toAttachmentSaveError(att, err)`.
     - Populate `savedNameById[att.id] = savedFilename`.
   - Return `{ savedNameById, errors }` (drop inline/other arrays).
   - Only non-inline IDs are present in `savedNameById`.

4) Implement inline placeholder processor (`src/helpers.ts:59-149` new helper)
   - `processInlinePlaceholders(email, paths, saveBinary)`:
     - Scan `email.markdownBody` for `![alt?](data:...)`:
       - Support whitespace/newlines between parts; tolerate MIME params like `image/svg+xml;charset=utf-8`.
     - For each placeholder (keep 0-based `placeholderIndex`):
       - Parse the data URI; require `;base64`. If missing or malformed:
         - Push `toAttachmentSaveError({ emailId: email.id, placeholderIndex }, 'Inline data URI is not base64')`.
         - Leave the original placeholder unchanged.
       - Determine MIME → extension via `getExtensionForMime`; fallback `.bin`.
       - Build base name with `buildAttachmentBase({ source: 'inline', emailId: email.id, index: placeholderIndex, suggestedName: altText?, mimeType })`.
       - Decode base64 to binary; on failure push `toAttachmentSaveError({ emailId: email.id, placeholderIndex, mimeType }, err)` and leave placeholder unchanged.
       - Call `saveBinaryData({ data, suggestedName: baseName, targetFolder, mimeType })` letting `uniqueFilename` handle collisions across inline/API.
       - On success, replace the placeholder with `![[<relative/path/filename>]]` using the same target folder resolution as non-inline attachments.
     - Return `{ body, inlineEmbeds, errors, inlineMeta }`:
       - `body`: modified markdown body.
       - `inlineEmbeds`: map from placeholderIndex to saved filename (post-unique).
       - `inlineMeta`: optional array of contexts for diagnostics (emailId, placeholderIndex, mimeType?, alt?).
       - `errors`: array of widened `AttachmentSaveError`s.

5) Update Markdown rendering (`src/helpers.ts:44-168`)
   - `renderEmailMarkdown(email, paths, savedNames?)` now:
     - Calls `processInlinePlaceholders(email, paths, saveBinaryData)` to get `{ body, inlineEmbeds, errors: inlineErrors }`.
     - Builds `## Attachments` section using `savedNames` (non-inline only) and the resolved attachment folder.
     - Assembles final markdown: frontmatter → body → attachment section.
   - Streamline `RenderedMarkdown` type:
     - Remove `inlineAttachments`/`otherAttachments`.
     - Add `inlineEmbeds` (placeholderIndex → filename) and `inlineErrors` (array of widened `AttachmentSaveError`).
   - Delete legacy `splitAttachments` and `replaceInlinePlaceholders` once the new processor is in place.

6) Wire inline errors into sync (`src/pipeline.ts:86-165`)
   - Use `resolveAttachmentTarget` to obtain `{ noteFolderPath, attachmentTargetPath }`; pass these to both `saveAttachments` and `renderEmailMarkdown`.
   - After `renderEmailMarkdown`, append `inlineErrors` to `attachmentErrors` so summaries include inline failures.
   - Ensure the inline filename map (if kept) is available for diagnostics/logging; not required for core rendering.

7) MIME and parsing guardrails
   - Use `getExtensionForMime`; default to `.bin` on unknown/invalid MIME; optionally guard against unsafe extensions.
   - Handle malformed data URIs gracefully:
     - Record an `AttachmentSaveError` via `toAttachmentSaveError`.
     - Keep the original placeholder; continue processing others.

8) Verification (execute in this order)
   - Inline + regular attachments:
     - Send email with both inline data-URI images and download-required attachments.
     - Expect API inline records skipped; inline files written from data URIs; deduped names across both sources; `attachmentErrors` reports any inline decode/save issues.
   - Collision handling:
     - Create inline and non-inline attachments with same suggested names; confirm `uniqueFilename` adds suffixes consistently via shared saver.
   - Regression for non-inline only:
     - Email with only non-inline attachments still creates folders and saves files; no inline processing errors emitted.

9) Tests (unit + integration smoke)
   a) Harness: add Vitest (or Jest) + `obsidian` fakes; use fake timers for scheduler tests; stub vault with in-memory file map and mock `downloadAttachment`.
   b) `attachments.ts`:
     - `buildAttachmentBase` picks sanitized filename when provided, falls back to `attachment-<id>-<index>`/`inline-...`, and appends MIME-derived extensions when missing.
     - `getExtensionForMime` strips params and maps known MIME types; defaults `.bin` on garbage/null.
     - `resolveAttachmentTarget` creates note + attachment folders as needed, keeps root untouched, and returns attachment target equal to note folder when `attachmentFolder` is empty.
     - `saveBinaryData` de-dupes via `uniqueFilename` when collisions occur and writes binary bytes intact.
     - `saveAttachments` skips `contentDisposition === 'inline'`, surfaces download/save errors in `errors`, and returns map keyed only by non-inline IDs.
   c) `helpers.ts` inline processor:
     - Parses valid `![alt](data:<mime>;base64,AAA...)` even with whitespace/newlines; rejects non-base64 URIs with `AttachmentSaveError` and leaves markdown unchanged.
     - On base64 decode failure, records error and preserves placeholder; on success, writes via shared saver and replaces with `![[<targetFolder>/<filename>]]` respecting attachment folder vs note folder.
     - Collision test: inline + API attachments with same suggested name end up with unique filenames via shared saver.
   d) Markdown rendering/pipeline:
     - `renderEmailMarkdown` builds frontmatter + body + `## Attachments` list using non-inline map, and passes through inline errors/embeds.
     - Pipeline combines attachment + inline errors and uses the resolved paths from `resolveAttachmentTarget` only once per run.
   e) `main.ts` plugin shell:
     - `normalizeSettings` trims API key, normalizes folders (`''`/`.` => root when allowed), defaults invalid inputs, and preserves stored `lastRunAt` strings.
     - Scheduler tests with fake timers: enabling `periodicSync` clears prior interval and schedules new one; `triggerImmediate` runs a sync once immediately; disabling stops the timer.
     - `handleSync` guard: second call while `isSyncing` is true no-ops; successful sync updates `lastRunAt` and persists settings; error path surfaces Notice with message.
